# SuperH

## Variants

| Language ID | Spec | Notes |
|---|---|---|
| `SuperH:BE:32:SH-1` | sh-1.slaspec | |
| `SuperH:BE:32:SH-2` | sh-2.slaspec | |
| `SuperH:BE:32:SH-2A` | sh-2a.slaspec | SH-2A FPU, including double precision (`FPU_DOUBLE`) |
| `SuperH:BE:32:SH-2E` | sh-2e.slaspec | SH-2 plus the SH-2E single-precision FPU |
| `SuperH:BE:32:SH7058` | sh-2e.slaspec + sh7058.pspec | SH-2E with the SH7058 memory map, peripheral registers and reset vectors |

The SH-2E variants use `superh2e.cspec`: float arguments in fr4-fr11, integer arguments in
r4-r7, and r0-r7, fr0-fr11 and fpul killed by calls. It also defines the `__preserve_r4_r7` and
`__shc_runtime` models, which `SH7058_RawImageSetup.java` assigns to the routines that need them.

`sh7058.pspec` is generated by `sh-2e/tools/gen_pspec.py` from the CSVs in `sh-2e/notes/`. Edit
the CSVs or the script, then regenerate; don't edit the pspec by hand.

## SH7058 flash images

1. Import the 1 MB flash image as Raw Binary, base address 0, language `SuperH:BE:32:SH7058`.
2. Answer "No" to "Analyze now?".
3. Run `SH7058_RawImageSetup.java` (Script Manager, category Processors.SuperH). It fixes the
   memory blocks, lays down the vector tables, runs auto-analysis and then applies the per-ROM
   steps (GBR values, calling conventions and so on).

An image that keeps calibration data in flash can split that range off as its own writable
block before the setup script runs (a pre-script of your own, ahead of `pre`), so that reads of
calibration scalars stay references instead of being folded into constants. The setup script
treats only the block at address 0 as FLASH and leaves any other block as it finds it.

Headless:

```
analyzeHeadless <proj> <name> -import rom.bin -loader BinaryLoader -loader-baseAddr 0
  -processor SuperH:BE:32:SH7058 -cspec default
  -preScript SH7058_RawImageSetup.java pre -postScript SH7058_RawImageSetup.java
```

The script's header lists every step and option. Steps marked HEURISTIC in its log, such as VBR
and GBR resolution, extra function entries, calling-convention
detection and committed prototypes, are worth checking on each new ROM.

- It creates functions at pointer-table targets, literal-pool tail-jump targets and push-started
  code after a literal pool (OS services, interrupt-handler bodies), so that code gets decompiled.
- It commits parameter lists (tag `SH7058SETUP_PARAMS`, return values left open) where the
  decompiler, a register dataflow and the call sites agree. Ghidra does not run Decompiler
  Parameter ID on a raw binary, and without it each call site guesses its arguments and drops
  registers whose value is also used elsewhere.
- It decompiles every function that reads an IO register and puts a pre-comment on each read the
  C does not use ("dummy read of TCSR at 00001234").

If you create functions or change code afterwards, run the script again with `only:models` and
then `only:ioreads`. That gives the new functions prototypes and dummy-read comments.

Headless decompiler scripts should call `DecompInterface.setOptions(new DecompileOptions())`.
Without it, read-only memory isn't respected, and globals show as `PTR_` indirections.

To use the manual lookups (`superh2e.idx`), copy `sh-2e-software-manual.pdf` into the
installed `Ghidra/Processors/SuperH/data/manuals/`.
